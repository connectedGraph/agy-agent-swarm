# agy-agent-swarm 代码审查

日期：2026-11-26
范围：`app/`、`server/`、`components/`、`lib/`、部署与构建脚本
依据：读代码 + 运行中实例（127.0.0.1:3100、9000）实测

## 结论

核心链路（会话 → 显式执行 → 沙箱执行 → 合并 → 检查 → 返工 → 验证 → 裁决）是通的，但边界没画干净：
单进程里混着 HTTP/SSE、LLM 编排、git 写操作和同步子进程；会话与任务各有一套消息模型；
任务状态与裁决结果是两个真相；流式事件全量重发。结果就是界面会卡、状态会说谎、
任务无法停止或清理，接口有两套并行入口。

下面按严重程度列。每条都标了位置。

---

## P0 正确性与安全

1. **FAIL 的任务显示成绿色「完成」**
   `runTask` 结尾无条件 `task.state = "done"`（server/orchestrator.ts:936-938），
   而 `STATE_LABEL.done = 完成`、`STATE_TONE.done = ok`（components/console/shared.tsx:20,34）。
   实测任务 `91b030e4` 裁决 FAIL、`71689d6b` 裁决 FAIL，侧栏与顶栏都是绿点「完成」。
   顶栏同时只显示 `STATE_LABEL`，不显示 verdict。用户会以为任务成功。
   修法：状态与裁决分离；顶栏按 `verdict.pass` 显示「完成 / 未通过」，或新增 `rejected` 状态。

2. **契约里的 verify 命令来自 LLM，却在宿主机裸跑**
   `verify()` 把模型产出的 `contract.verify` 直接交给 `execFileSync("bash", ["-lc", cmd])`
   （server/orchestrator.ts:435, 456-458）。黑名单 `BANNED_CMD`（:451）只挡了
   `rm -rf /`、`sudo`、`mkfs`、`curl|sh` 这几种，`python -c`、`node -e`、`sh -c`、
   `git clean -fdx`、改 `~/.bashrc` 都拦不住。执行代理本身在 bubblewrap 里，
   检查命令反而不在；这是权限倒挂。`detectChecks` 的 `npm test`（:398）同样在宿主跑，
   等于执行模型写的任意脚本。
   修法：检查命令进 bwrap（只读根 + 可写 integration），或至少改成白名单 + 不允许 shell 元字符。

3. **网关把「录盘失败」记成上游 502**
   `appendFileSync` 写在代理请求的同一个 try 里（server/gateway.ts:206-217 → 218-225）。
   录制目录不可写时直接进 catch，`call.status = 502`，即使上游已经 200。
   实测 `recent` 里 5 条 `GET /v1beta/models` 全是 502、0 token，
   真实 error 是 `ENOENT .../projects/agent-swarm/data/gateway/record-*.jsonl` ——
   `DATA_DIR` 取的是模块加载时的 `process.cwd()`（:9），改目录名后进程仍握着旧绝对路径。
   前端 `GatewayCard` 又不显示 `error`，只剩一排看不懂的 502。
   修法：路径锚 `SWARM_APP_ROOT`；录制失败单独捕获，不污染上游状态；UI 展示 error。

4. **一个会话只能执行一次，重跑会丢旧任务**
   `startChatTask` 直接覆盖 `chat.taskId`（server/chats.ts:191-193），
   而 UI 用 `canRun = !task`（components/chat/ChatApp.tsx:203）把「开始执行」永久藏掉。
   服务端其实允许任务结束后再执行，但前端没有入口；一旦重新执行，旧任务从侧栏消失，
   只剩 store 里的孤儿数据。任务失败（如规划阶段报错）也没有重试入口。
   修法：`Chat.taskIds: string[]`（或 runs 列表），侧栏按最近一次展示并提供历史；加「再执行一轮」。

5. **不能取消、不能停止**
   `createTask` 里 `void runTask(task)`（server/orchestrator.ts:1002），没有返回句柄、
   没有 abort、没有终止接口；`runAgyTask` 只有 10 分钟硬超时。
   一个跑飞的 8 代理集群只能等它自己结束，或者重启服务（重启后任务被标为「中断」）。
   修法：任务级 AbortController + 子进程组 kill；POST /api/tasks/:id/cancel；
   前端执行中显示「停止」。

6. **执行目标取「最后一条用户消息」**
   `startChatTask` 用 `reverse().find(...)` 取最后一条 user 文本（server/chats.ts:183）。
   用户最后一句如果是「好的，开始吧」「就按这个做」，goal 就变成这句话，
   规划器只能瞎猜。正常产品应该用整段对话生成一份执行摘要，或让用户确认要执行的 goal。
   修法：执行前生成/确认 goal；至少把「最后一条」限定为包含目标的长度或显式选择。

7. **运行目录无人回收**
   `data/runs/` 现有 19 个目录，其中 12 个既没有对应 task 也没有 chat（实测），
   每个含 worktree / integration / 临时 repo。`cleanupTask` 已实现但从未接线
   （server/orchestrator.ts:1006），也没有 DELETE 接口。删任务文件还会在用户仓库的
   `.git/worktrees` 留注册项。
   修法：删除/归档 API + 统一清理（worktree remove + 目录 + 任务 JSON），或定期 GC。

8. **本地 API 无鉴权、无 Origin 校验**
   所有写接口（建会话、跑任务、合 main）都没有 token/CSRF 防护（app/api/**）。
   目前只监听 127.0.0.1，但这挡不住同机浏览器里的任意网页发起请求（PNA 不是保证）。
   `promote` 合入用户仓库且不可撤销。网关的 `/control/*` 还开了 CORS `*`（server/gateway.ts:74-78）。
   修法：至少一个本地 token（存 data/settings，前端从同源注入）+ Origin 校验。

## P1 架构与接口边界

9. **两套会话系统并存**
   `Chat.messages` + `chats.ts` 的 `sessions` Map，与 `Task.messages` + `orchestrator.ts` 的
   `bossChatSessions` Map（server/orchestrator.ts:78-148）是两套几乎一样的流式对话实现。
   UI 只渲染 `chat.messages`，`task.messages` 从不显示（components/chat/Transcript.tsx 全文），
   `chat` 事件前端也没处理（ChatApp 只处理 snapshot/session/task/agent/boss）。
   旧任务迁移后，历史上在任务里的追问在界面上消失。`/api/tasks/:id/messages` 成了死接口。
   修法：单一会话模型，任务只是会话里的一种事件/子记录；删掉一套 Map 和一套 API。

10. **双入口绕过对话**
    `POST /api/tasks` 仍然可以直接建任务执行（app/api/tasks/route.ts），
    与「先聊再执行」的产品约束冲突，README 也照旧宣传。其他 agent 或脚本一旦调它，
    就回到「一句你好开三个代理」的老路。
    修法：删掉或标记 deprecated；执行只从会话触发。

11. **同步子进程阻塞整个服务**
    合并、提交、diff、检查、worktree 创建全部用 `execFileSync`/`git`（server/orchestrator.ts:22-36, 435），
    `detectChecks` 还有 `statSync` 递归（:359-385），全部跑在服务 HTTP/SSE 的同一个事件循环里。
    一条检查最长 120 秒，多条串行；这段时间页面、SSE、其它请求一起冻住。
    这是「界面卡」的最大来源，不是 React。
    修法：执行层独立 worker 进程/线程（或至少 async spawn + 流式回传），Web 只读事件。

12. **规划与裁决全靠字符串启发式**
    `parsePlan` 猜 JSON 边界、兼容 4 种 schema（:183-218），`flatten` 拍平任意对象（:150-161）；
    失败一次后用一条中文提示重试（:522-533）；再失败就**编造** N 个任务
    （:207-217，每个代理「完成你编号对应的那部分」）。裁决 prompt 要求输出
    `PASS: ...`（server/prompts.ts:163-172），代码却先尝试 JSON（:798-814），两边协议不一致。
    修法：结构化输出 + schema 校验（zod）；校验失败明确失败，不要造任务。

13. **依赖契约是假的**
    `WORKER_PREAMBLE` 承诺「依赖方的提交已包含在你的工作目录中」（server/prompts.ts:52-53），
    实际只取 `deps[deps.length - 1]` 一个提交作为 baseRef（server/orchestrator.ts:893-903）。
    多个 `depends_on` 时其余依赖不可见。规划返回任务数少于代理数时，
    多出来的代理都拿到最后一个任务（:538），静默重复劳动。
    修法：合并多个依赖为一个 base（或按依赖顺序建链），任务数不匹配时拒绝执行。

14. **账本口径会互相覆盖**
    `collectPiusage(session)` 返回整个 session 的累计值：`judge` 写进 `boss.summaryUsage`（:830），
    之后的任何追问又用 chat session 的累计值覆盖它（:141）。aggregate 的用量完全没记账。
    `recount`（:950-957）因此系统性少算。界面上同一个任务还有两个 token 总数：
    右栏头是代理之和，账本是 `totalUsage`（实测 371.3k vs 762.9k，无标签区分）。
    修法：按阶段增量记账，字段分开；UI 只展示一个权威总额并说明构成。

15. **持久化两份实现、两个路径基准**
    `store.ts` 有 tmp+rename 的 `persistNow`（:27-39）和无原子写的 `persistTask`（:104-111）；
    `chats.ts` 又抄了一份 atomic write（:67-77）。
    `TASKS_DIR` 默认 `process.cwd()`（store.ts:17），而 chats/orchestrator 用 `SWARM_APP_ROOT`；
    不设 `SWARM_TASKS_DIR` 时任务与会话会落到不同地方。
    `SWARM_CHATS_DIR` 也没写进 README 的环境变量表。
    修法：一个 `paths.ts` + 一个原子写工具；store/chats 都从它取路径。

16. **GET 接口有写副作用**
    `GET /api/tasks/:id/diff` 里执行 `git add -A`（app/api/tasks/[id]/diff/route.ts:9-12），
    会改 agent worktree 的 index。且这个接口在新 UI 里根本没人调用。
    修法：只读 diff（`git diff --stat` 基于 HEAD），或改成 POST 并说明。

17. **任务状态没有状态机**
    `task.state = ...` 散落在 20 多处，没有合法迁移校验；`done` 同时表示
    「流程结束」和「成功」，与 `verdict.pass` 冲突（见 P0-1）。
    修法：显式状态机 + 单一迁移函数；成功与否只由 verdict 表达。

18. **会话内存不回收**
    `chats.ts:115` 与 `orchestrator.ts:85` 的 Map 永久持有 pi session（含完整历史、ModelRuntime）。
    长开的服务里会话越多内存越大，也没有上下文窗口管理（长会话会撑爆上下文）。
    修法：LRU + 空闲淘汰；历史按轮摘要或截断。

## P2 性能

19. **每个 token 增量都重发整个对象**
    代理：`onText` 每个 chunk 赋值 `agent.text` 后 emit 整个 agent（server/orchestrator.ts:588-591）；
    会话：每个 text_delta 广播整个 chat（含全部历史消息，server/chats.ts:152-157）。
    对一段 n 字符的输出，总流量是 O(n²)。当前 6 个任务的 snapshot 首帧实测 141 KB
    （`/api/stream`），每个新标签页/断线重连都全量推一遍，没有分页。
    修法：只发增量（agentId + delta），客户端拼接；snapshot 只发摘要，正文按需拉。

20. **每个 400ms 全量重写任务 JSON**
    `schedulePersist` 防抖后把整个 task（6 个任务的 JSON 目前 12–29 KB，含全部 agent 文本）
    序列化重写（server/store.ts:42-53）。长任务 + 大输出时写放大明显。
    修法：文本流单独 append 或落文件，状态 JSON 只存结构化字段。

21. **前端每个 delta 全量重渲染**
    `session`/`agent` 事件都替换整个数组（components/chat/ChatApp.tsx:48-70），
    `Transcript` 每次 `map` 全部消息，`RichText` 重新解析 Markdown；
    滚动 effect 依赖消息数组引用，每个 delta 都 `scrollTo` + 读 `scrollHeight`（:113-115）。
    长会话 + 高频流式会明显掉帧。
    修法：消息组件 memo、只更新最后一条、rAF 批处理、流式期间不重排历史。

22. **检查项探测是 4 次同步全树遍历**
    `detectChecks` 对 `.py/.sh/.mjs,.cjs/.html` 各调一次 `walkFiles`（:391-428），
    每层 `statSync`；skip 列表没有 `.venv`、`target`、`vendor`、`coverage`。
    大仓库合并后会卡住整个进程。
    修法：一次遍历收集、异步、加 skip 列表、限制深度。

23. **SSE 没有事件 id / 断点续传 / 订阅过滤**
    `/api/stream` 一个连接收全量事件（app/api/stream/route.ts），
    断线后只能靠 snapshot 重建；前端不区分当前会话，所有任务事件都推给所有标签页。
    修法：`id:` + Last-Event-ID；按 chatId 订阅。

24. **网关轮询**
    前端每 4 秒拉一次 `/api/gateway`（ChatApp:79-96），网关每次重算 `recent`/`byAgent`。
    网关其实已经有数据，应该走 SSE；离线时每 4 秒产生一条失败记录。

## P3 UI / UX

25. **窄屏功能直接消失，不是折叠**
    `@media (max-width: 1180px)` 把 `.agent-rail { display: none }`，
    但「查看执行详情」按钮仍会设置 selectedAgent，点了没反应；
    `@media (max-width: 820px)` 把 `.chat-side { display: none }`，
    没有汉堡/抽屉，760px 下无法切换会话、没有品牌、没有主题切换（实测截图）。
    修法：右栏做成可开合抽屉；侧栏在窄屏用 sheet；保留入口。

26. **没有删除 / 归档 / 重命名 / 清空**
    左侧只有「新建会话」。用户要删掉一条失败任务只能让 agent 手动改文件。
    没有任务清理、没有项目删除。这是「不好用」里最直接的一条。

27. **执行中完全禁聊**
    `disabled={running}` 把输入框锁死（ChatApp:292），一轮可能十分钟。
    不能追问、不能补充约束、不能停止。修法：允许排队或「打断并追加」，并提供停止。

28. **刷新后永远停在空状态**
    初次加载不自动选中任何会话（ChatApp 没有恢复 lastChatId 的 effect），
    每次刷新都看到「新建会话」和示例，需要重新点。修法：记忆上次会话（localStorage + 服务端校验）。

29. **仓库路径只能新建时填，且会残留**
    `repoPath` 输入只在 `isNew` 显示（Composer:56-64）；`newChat()` 不重置 `repoPath`
    （ChatApp:195-200），下一条新会话会带着上一条的仓库路径，容易误跑。
    创建后也不能改仓库。修法：会话设置里可改；新建时清空；对不存在的路径即时校验。

30. **没有项目实体，只按目录名分组**
    `projectName()` 取路径最后一段（Sidebar:9-13），两个不同路径下的同名目录会合并，
    组顺序随更新时间跳动；没有搜索、折叠、排序。与「抄 kanna」的项目模型不符。
    修法：真正的 Project（id/名称/仓库/默认分支），会话挂在项目下。

31. **看不到产出**
    `/api/tasks/:id/diff` 没接线；`AgentDetail` 只列前 4 个文件，worktree 路径不可点；
    没有 diff 视图、没有 integration 树入口、没有合并后的文件清单。
    用户只能自己去文件系统找。修法：任务详情加「改动文件 / diff / 打开目录」。

32. **错误不进入对话流**
    发送失败只显示在输入框上方一行（ChatApp:282-286），刷新即失；
    任务同时有 summary 和 error 时，`task.error` 被隐藏（Transcript:81）。
    失败任务没有「重试/继续」按钮，只有再聊。
    修法：错误作为会话里的一条系统消息；失败卡片带重试。

33. **危险动作没有确认**
    「开始执行」紧贴发送键（Composer:84-90），点一下直接起默认 3 个代理、
    建分支、烧 token，没有二次确认。发送键用对勾图标（Composer:111），语义也不对。
    修法：执行前弹出目标 + 代理数 + 仓库的确认；发送用箭头。

34. **信息口径不一致**
    右栏头「371.3k tokens」是代理之和，账本「762.9k」是含编辑器的总额；
    返工卡「2 轮 / 0 轮修复」里的 0 是「成功修复数」，文案读起来像「没修过」。
    修法：统一命名（「执行代理合计 / 全部合计」「2 轮，均未产生改动」）。

35. **时间信息缺失**
    任务卡不显示开始/结束/耗时（`dur()` 已存在但没用在会话页）；
    消息只有 HH:mm，跨天会话无法分辨。修法：相对时间 + 悬浮完整时间。

36. **无障碍与移动端细节**
    侧栏项/代理项是无可读标签的 `button`（title 才有），焦点样式缺失；
    `--ink-4` 小字号对比偏低；`height: 100vh` 在移动端会被地址栏顶住（用 100dvh）；
    示例 chip 只填草稿不发送，用户还要再点一次。

## P4 清理与工程化

37. **约 800 行死代码**
    `components/Console.tsx`、`console/TaskRail.tsx`、`Stage.tsx`、`EmptyState.tsx`、
    `BossCard.tsx`、`AgentCard.tsx`、`SummaryCard.tsx` 只被彼此引用，页面已不用；
    旧仪表盘 CSS 也还留在 globals.css 前 650 行。
    未使用的导出：`cleanupTask`、`getRecordState`、`tasksDir`；
    `SwarmEvent` 里的 `log`/`record`/`gateway` 从未 emit。
    修法：整体删除，减少阅读成本和构建体积。

38. **没有测试**
    没有单测、没有 lint 脚本；`package.json` 无 `test`。规划解析、状态迁移、
    路径处理这些最该测的部分全靠手测。至少给 `parsePlan`、`normalizeTask`、
    `recount`、`startChatTask` 加纯函数单测。

39. **错误被静默吞掉，没有日志**
    `persist`/`loadChats`/`loadTasks`/`gateway` 大量空 catch；
    服务端没有请求日志、任务事件日志，`journalctl` 是空的（实测 `-- No entries --`）。
    出问题时只能翻 JSON。
    修法：结构化日志（任务 id、阶段、耗时、错误）+ 落盘 event log。

40. **文档与实现漂移**
    README 仍把 `/api/tasks` 作为正常入口、宣称「验证在沙箱」但检查命令不在；
    `SWARM_CHATS_DIR`、`GATEWAY_RECORD` 没进环境变量表；
    「任务状态：… → 完成 / 失败」没有提到 verdict 与 state 的双轨。

## 建议的修复顺序

1. P0-1 状态与裁决分离（半天，直接消掉「假成功」）
2. P0-3 网关错误归类 + P0-4/P0-5 任务可重跑/可取消（一天，恢复基本操作）
3. P1-11 执行层异步化（把同步子进程移出事件循环，收益最大）
